# Permissions explained
Permissions work in **layers**:
1. **Server-wide role permissions** (Server Settings > Roles)
2. **Category overrides** (a channel category's permissions)
3. **Channel overrides** (one specific channel)

Each permission has three states: **allow (tick)**, **deny (cross)** and **inherit (slash)**. A deny on the channel beats an allow from a role.

**Hiding a channel from everyone**
Channel > Permissions > `@everyone` > **View Channel: deny**. Then add your staff role and **allow View Channel**. Do this on the **category** and let channels **sync** to it.

**Read-only channel**
`@everyone`: allow View Channel, **deny Send Messages**, deny Add Reactions if you want. Staff roles: allow Send Messages.

**Sync permissions:** channels inside a category can stay *synced* with it, so changing the category updates all of them. Only break sync when you need a special case.

**Dangerous permissions (give sparingly)**
- Administrator
- Manage Server, Manage Roles, Manage Channels
- Manage Webhooks
- Ban Members, Kick Members
- Mention @everyone
- Manage Messages (powerful in public channels)

**Test with "View Server As Role"**
Server Settings > Roles > the three-dot menu > **View Server As Role**. This shows exactly what a role sees, so you catch leaks before members do.

**Common mistakes**
- Giving a role *Administrator* "just to make it work": it bypasses every deny
- Forgetting a category override, so a "private" channel shows to everyone
- A bot role below the role it should manage
- Allowing `@everyone` to create invites in a hidden channel

**Verification gate:** a simple pattern is an `Unverified` role that only sees the rules/verify channel, and a `Member` role granted after verification (by button, bot or onboarding).

Checkpoint: use View Server As Role for `@everyone` and `Member`. Do they see exactly what you expect?
